# Component D — cluster robustness — stage D.4 of D.1–D.4 (WebSocket speed under load)

Build ONLY this stage now. Earlier stages must already pass. Check: `bash /spec/d/checks/check_d_4.sh`.

**Functions used from earlier stages:** `ws_handler` polling loop, `create_message`, `emit_event`

**Functions added in this stage:** tune the polling loop and SQLite settings only

Target (from the grading contract): under concurrent writes across all three nodes, `message.created` delivery per subscriber has median latency ≤ 300 ms, p95 ≤ 800 ms, and ≤ 1% missing events.

How to get there with the required design: poll `events` every 50 ms (one indexed query: `WHERE channel_id IN (...) AND event_id > ?`), send all new rows in one go, open SQLite with `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, keep write transactions short (no network I/O inside them), and use `ThreadingHTTPServer` with `daemon_threads = True`.

Every `message.created` frame carries the full `message` (MessageObj, including `body`); the check matches frames to posts by `message.body`.

| ID | Behaviour | Required result |
|---|---|---|
| D4.1 | 3 subscribers (one per node); 3 writers (one per node) post 25 messages each concurrently | every POST `201` |
| D4.2 | each subscriber | receives ≥ 99% of the 75 `message.created` frames |
| D4.3 | latency from POST send to frame receipt, per subscriber | median ≤ 300 ms |
| D4.4 | same | p95 ≤ 800 ms |
| D4.5 | ids received by each subscriber | strictly increasing, no duplicates |
