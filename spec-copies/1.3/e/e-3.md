# Component E — IRC, web UI and message edits — stage E.3 of E.1–E.5 (IRC channels and web bridge)

Build ONLY this stage now. Earlier stages must already pass. Check: `bash /spec/e/checks/check_e_3.sh`.

**Functions used from earlier stages:** `create_message` (same function the HTTP route uses, so it runs `emit_event` in the same `BEGIN IMMEDIATE` transaction), `join_channel`, `workspace_by_slug`

**Functions added in this stage:** `irc_name(ws_slug,channel_name)` = `#<slug>/<name>`, `resolve_irc_channel(name)`, `irc_poll_loop(conn)` (polls `events` every 50 ms for joined channels)

| ID | Behaviour | Required result |
|---|---|---|
| E3.1 | `JOIN #<slug>/<channel>` (a public channel; the user is joined to it like `POST /join`) | `:<nick>!<user>@huddle JOIN #<slug>/<channel>`, then `353` (names list), then `366`; `331`/`332` may come before `353` |
| E3.2 | `JOIN #<slug>-<channel>` or any unknown name | `403 <nick> <name> :No such channel` |
| E3.3 | `PRIVMSG #<slug>/<channel> :hello from irc` | the message appears in `GET /api/channels/{id}/messages` with that body and the IRC user as author |
| E3.4 | WebSocket subscriber of the channel during E3.3 and a web POST | `message.created` frames with dense ids across both writers (IRC and web) |
| E3.5 | a web `POST /api/channels/{id}/messages {"body":"hi irc"}` by user `bob` | the IRC client receives `:bob!bob@huddle PRIVMSG #<slug>/<channel> :hi irc` within 2 s (never echo an IRC client's own PRIVMSG back to it) |
| E3.6 | `NAMES`, `TOPIC`, `WHO`, `LIST`, `MODE` on the joined channel | accepted (never `421`); `TOPIC #chan` answers `332` or `331` |
| E3.7 | `SIGKILL` the HTTP node on 8000, then a web POST on 8001 | the IRC client still receives the PRIVMSG within 2 s; an IRC PRIVMSG still commits (visible over HTTP on 8002) |

Web posts reach IRC because `irc_poll_loop` reads new `message.created` / `message.reply` rows from `events`, never because an HTTP node talks to the gateway.
